API reference

Every tool the server exposes, grouped into 30 categories in 12 feature areas (239 tools total). Each entry shows the name, what it does, its parameters (required vs optional), and a canonical example. Wondering which RouterOS commands are not covered yet? See the API coverage.

Naming convention. A tool is named <verb>_<resource>: a verb — create, list, get, update, remove, plus category-specific verbs such as enable, move or flush — and what it acts on, for example list_interfaces, create_simple_queue or enable_safe_mode. These are the names the server registers, so they are what an MCP client lists and what you pass when you call a tool. Some clients show them qualified with the server name (Claude Code, for one, shows mcp__<server>__list_interfaces). Older releases and tutorials show many of them with a mikrotik_ prefix; the server no longer registers it, so use the names on this page. With a multi-device inventory configured, every device-scoped tool also accepts an optional device argument naming the inventory title to target.

Feature areas. The categories are grouped into the same feature areas as the packages under src/mcp_mikrotik/scope/, so a category's code, its unit tests and its reference pages are easy to find from one another in the repository; see Contributing. Failures are reported as failures. A write that RouterOS refuses, or that finds nothing to change (an id or a name that does not exist), is reported as a failure with RouterOS's answer instead of a success message.

Inventory — Multiple Devices

Manage a whole fleet from one server. Devices are declared in a YAML inventory; each entry has a unique title, and every device-scoped tool accepts an optional device argument naming the title to target. With no inventory configured the server behaves exactly as before — a single device built from MIKROTIK_HOST / MIKROTIK_USERNAME / …, and device can be omitted everywhere.

1 tool
category 01
list list_devices

Lists the devices this server manages — title, host, port, username, tags, and region. Credentials are never returned. Use it to discover the fleet before targeting a device.

—no paramsTakes no arguments
Fleet patternlist_devices() # discover the fleet list_interfaces(device="office-core") # target one device create_vlan_interface(device="branch-berlin", name="vlan100", vlan_id=100, interface="ether1")
configure Configuring the inventory

The inventory is YAML, from one of two sources — MIKROTIK_INVENTORY_FILE (path to a YAML file, recommended) or MIKROTIK_INVENTORY (the inventory written inline; YAML flow syntax needs no escaped quotes, and plain JSON works too since it's a YAML subset). When both are set, the inline value wins. A broken inventory (missing file, bad YAML, invalid entry) stops the server at startup with one clear message. A ready-to-copy template ships at the repository root as inventory.example.yml.

select Selecting a device

Every device-scoped tool takes an optional device argument. One device configured — omit it; that device is used automatically. More than one — pass the title. Omitting it, or passing an unknown title, returns an error that lists the valid titles, so an AI caller corrects itself on the next call instead of quietly running the command on the wrong router.

DOCKER
In the container, the inventory file must be mounted as a volume — the image ships /config as the mount point: -v "$PWD/inventory.yaml:/config/inventory.yaml:ro" -e MIKROTIK_INVENTORY_FILE=/config/inventory.yaml. Two traps the entrypoint catches with an explicit error: the container runs as uid 1000, so the file must be readable by that uid (chmod 644 is usually enough); and if the host file doesn't exist at start, Docker silently creates a directory in its place — create the YAML first. The entrypoint also accepts --inventory '<yaml>' / --inventory-file <path>. When an inventory is configured it wins, and MIKROTIK_HOST / MIKROTIK_USERNAME / MIKROTIK_PASSWORD / MIKROTIK_PORT / MIKROTIK_ALLOW_SSH_AGENT / MIKROTIK_SSH_AGENT_KEY are ignored. See Installation.
BEHAVIOR
Connections are per command — every command opens its own SSH connection and closes it when done, so parallel client sessions can't disturb each other; the trade-off is one SSH handshake per command. Safe mode is per device — each device holds its own persistent session, so enable_safe_mode(device="office-core") leaves every other device untouched. The inventory is a secret — it holds fleet credentials, so prefer key_filename, restrict file permissions, and remember env values show in docker inspect. Validation errors never echo inventory contents, so a typo can't leak a password into a log. For a local two-device lab, routeros-docker/docker-compose.yml starts routeros-a (SSH 127.0.0.1:2222) and routeros-b (:2223).

Safe Mode — Atomic Sessions

RouterOS safe-mode wraps a sequence of changes; if the management session drops before you commit, every change auto-reverts. Highly recommended when editing firewall or connectivity rules remotely.

4 tools
category 02
HOW IT WORKS
enable_safe_mode opens a persistent SSH shell and sends a Ctrl+X to the router. While active, every subsequent MCP tool call is routed through that same session automatically (the connector detects it — no per-command connections). commit_safe_mode sends a second Ctrl+X, writing the pending changes to flash/NVRAM and closing the session; rollback_safe_mode simply drops the session (no Ctrl+X), so RouterOS reverts everything. Pending changes live in memory only — a router reboot, not just a dropped connection, also reverts them. Concurrent calls are serialised through an internal lock, so parallel requests are safe. With an inventory, safe mode is tracked per device — enabling it on one router leaves the others untouched.
enableenable_safe_mode

Starts a safe-mode session; afterwards every tool call runs inside the one persistent shell until you commit or roll back. Returns an Error: … string if the SSH connection fails or the router doesn't confirm the <SAFE> prompt.

—no paramsTakes no arguments
commit · rollbackcommit_safe_mode · rollback_safe_mode

Persist the journaled changes, or revert them immediately. Both are no-ops when safe mode isn't active — they return "Safe mode is not active. Nothing to commit / roll back."

statussafe_mode_status

Reports whether a safe-mode session is currently active — e.g. "Safe mode is ACTIVE. Changes are pending — NOT yet persisted…" versus "Safe mode is NOT active…".

Firewall Raw — Pre-conntrack Rules

Tools for the RouterOS raw tables, /ip firewall raw and /ipv6 firewall raw. Raw rules run before connection tracking, in the prerouting and output chains. They are used to drop unwanted traffic cheaply (for example traffic from a blocklist, or bogons on the WAN) and to exempt traffic from connection tracking with action=notrack. Raw rules see no connection state, so there is no connection_state matcher.

Each tool exists twice, with the same parameters: *_raw_rule(s) for IPv4 and *_ipv6_raw_rule(s) for IPv6. The only parameter that differs is the TTL matcher, ttl for IPv4 and hop_limit for IPv6. In IPv6 the ICMP protocol is spelled icmpv6. With --read-only, only list_* and get_* are exposed.

Address Lists — Named IP Sets

BEHAVIOR
Three things worth knowing before you use these. IPv6 stores host entries with an explicit /128 — adding 2001:db8::5 stores 2001:db8::5/128, so a bare lookup wouldn't match; these tools canonicalise the address for you, so either form works. List names match exactly, including spaces — "internal NS " with a trailing space is a different list from "internal NS"; nothing is trimmed. A hostname entry creates dynamic children — address=example.com adds one static entry plus one dynamic entry per resolved address (use static_only to exclude them), and an entry with a timeout is likewise dynamic and does not survive a reboot.

Area · VPN

IPsec — Peers, Policies and Tunnel State

Read-only views over the IPsec subsystem (/ip ipsec): which peers, policies, profiles and proposals are configured, and the live state of the tunnels. Output is returned as RouterOS prints it, including the Flags legend.

/ip ipsec identity is deliberately not exposed: its print detail output carries secret= in clear text, and no read tool should be able to surface a pre-shared key. Peers, policies, profiles and proposals show the same topology without the credential.

6 tools
category 30
list list_ipsec_peers

Lists the configured IPsec peers. Runs /ip ipsec peer print detail.

name_filter · address_filteroptionalFilter by peer name or address (substring match)
Examplelist_ipsec_peers(name_filter="branch")
list list_ipsec_policies

Lists the IPsec policies with their phase 2 state. Runs /ip ipsec policy print detail. The Flags legend separates configured policies from the ones a peer generated at runtime (D), and ph2-state says whether the child SA is established. A policy whose selectors do not match the far end's is the usual cause of a tunnel that comes up and passes nothing.

peer_filteroptionalFilter by peer name (substring match)
src_address_filter · dst_address_filteroptionalFilter by selector (substring match). These are the encapsulated subnets, not the tunnel endpoints
Examplelist_ipsec_policies(dst_address_filter="10.20.0.0/24")
list list_ipsec_profiles

Lists the IPsec profiles (phase 1: DH group, hash, encryption, lifetime, DPD). Runs /ip ipsec profile print detail. The phase 1 lifetime must be longer than the phase 2 lifetime on the proposal, so the child SA rekeys inside a live parent SA; equal lifetimes tear the tunnel down on every rekey. dpd-interval multiplied by dpd-maximum-failures is how many seconds of silence the peer tolerates.

name_filteroptionalFilter by profile name (substring match)
Examplelist_ipsec_profiles()
list list_ipsec_proposals

Lists the IPsec proposals (phase 2: encryption, authentication, PFS, lifetime). Runs /ip ipsec proposal print detail. Compare lifetime against the phase 1 lifetime on the profile, and against whatever the far end proposes; a cloud provider's own SA lifetime counts as a third value.

name_filteroptionalFilter by proposal name (substring match)
Examplelist_ipsec_proposals(name_filter="default")
get get_ipsec_active_peers

Lists the peers with a live IKE session, with uptime and counters. Runs /ip ipsec active-peers print detail. This is the parent (phase 1) side: state, uptime, last-seen and the byte counters. A peer can sit here established while its child SAs carry nothing; use get_ipsec_installed_sa to tell the difference.

remote_address_filteroptionalFilter by remote address (exact match)
state_filteroptionalFilter by session state, e.g. established (exact match)
Exampleget_ipsec_active_peers(state_filter="established")
get get_ipsec_installed_sa

Lists the installed security associations (child, phase 2 SAs). Runs /ip ipsec installed-sa print detail. The Flags legend is the point of this view: S (SEEN-TRAFFIC) is the only field that separates an SA carrying traffic from one that is merely installed, H means the cipher runs in hardware and E means ESP. A missing S can mean idle, not broken: put traffic over the selector before concluding anything. Once a peer has several child SAs, per-SA counters do not map onto policies, so watch which counters move under traffic you control instead of pairing SAs by hand.

src_address_filter · dst_address_filteroptionalFilter by SA endpoint (substring match). These are the tunnel endpoints (public addresses); behind NAT-T they carry the port, e.g. 198.51.100.2:4500
Exampleget_ipsec_installed_sa(dst_address_filter="198.51.100.2")
